# جستجوی شهر مرجع هتل — ۲۰۲۶-۱۰-۲۰

## قرارداد و مالکیت

مرجع انتخاب مقصد، تمام شهرهای فعال `references.cities` است، حتی مقصد خارجی یا شهری که نگاشت پرووایدر ندارد. Hotels اطلاعات مرجع را فقط از `References.Application.Contracts` و MediatR دریافت می‌کند. دریافت فهرست شهر هیچ تماس خارجی، write یا sync کاتالوگ ندارد.

- `GET /api/hotels/v2/cities?name=...`: پاسخ یکپارچه شامل `referenceCityId`, `name`, `nameEn`, `provinceId`, `provinceName`. نام خالی همه شهرهای فعال را با ترتیب مرجع می‌دهد؛ جستجوی نام فارسی/انگلیسی، فاصله و ی/ک عربی را نرمال می‌کند.
- `GET /api/hotels/v2/availability/city?referenceCityId=...&checkin=...&checkout=...&parties=...`: فقط شناسه مرجع معتبر و فعال. پارامترهای قدیمی `cityId` و `cityKey`، حتی همراه شناسه جدید، خطای ۴۰۰ فارسی می‌دهند.
- سایر قراردادهای V2، `HotelKey`, `OfferToken`, فیلترها و مبلغ `long` به ریال حفظ شده‌اند. جزئیات و quote همچنان به منبع و شناسه بومی پیشنهاد متصل‌اند.

هر adapter با `ResolveCityIdsAsync` جدول خودش را می‌خواند: `hotels.snapptrip_city_mappings` و `hotels.lamaso_city_mappings`. لاماسو فقط نگاشت فعال می‌خواند. نگاشت‌ها Cache نمی‌شوند؛ تنظیمات قدیمی CityMappings/CityCountries/CityCodes دیگر منبع جستجو نیستند. نام مشابه یا کشور حدسی جای نگاشت تأییدشده را نمی‌گیرد. نگاشت‌های SQL با EF خوانده می‌شوند و از migrations ساخت جدول مستثنا هستند؛ مدیریتشان همچنان با اسکریپت‌های جغرافیا است.

پرووایدرها موازی، شناسه‌های بومی متعدد هر پرووایدر ترتیبی جستجو می‌شوند. Cache availability موجود با شناسه بومی و تمام شرایط سفر حفظ شده است. تکرار دقیق هتل/اتاق/نرخ/واسطه در همان پرووایدر حذف می‌شود؛ پیشنهاد دو پرووایدر ادغام نمی‌شود.

## ارتقای داده و انتشار

1. پیش از انتشار، ساختار و داده محیط مقصد را بررسی کنید. وجود اسکریپت در مخزن، اثبات اجرای آن در محیط نیست.
2. اسکریپت `scripts/hotels/geography/2026-10-19-v4/2026-10-19-v4-complete.sql` باید پیش از migration جدید روی محیط نصب شده باشد. اجرای آن مطابق runbook جغرافیا، با پشتیبان و بررسی تعارض‌ها است؛ این تغییر آن را خودکار در startup اجرا نمی‌کند.
3. migration `20261020081100_HotelsReferenceCitySearch` نبود جدول‌های نگاشت یا ستون `lamaso_city_mappings.IsEnabled` را با خطای روشن متوقف می‌کند. سپس `catalogue_listings.ReferenceCityId` را اضافه و CityKey تاریخی را nullable می‌کند. Backfill فقط از Provider و NativeCityId دقیق انجام می‌شود؛ رکورد بدون نگاشت دست‌نخورده می‌ماند.
4. ابتدا schema، سپس Backend و سپس WebApp سازگار منتشر شوند. تمام کلیدهای هتل، پیشنهاد، رزرو و شناسه‌های بومی حفظ می‌شوند. جدول تاریخی catalogue_city_references حذف نمی‌شود، اما مسیر جدید آن را نمی‌خواند یا نمی‌نویسد.
5. rollback عملیاتی با بازگرداندن نسخه سازگار هر دو برنامه و حفظ schema افزایشی انجام شود. Down این migration عمداً متوقف می‌شود تا داده جدید یا شناسه‌های تاریخی از دست نروند. رکورد مالی یا رزرو برای rollback دوباره اجرا نشود.

جستجوی لاماسو تابع SearchEnabled موجود است. Purchase آن همچنان غیرفعال است و این تغییر آن را فعال نمی‌کند. لاگ‌های جستجو ReferenceCityId، پرووایدر، تعداد نگاشت، موفقیت/شکست و مدت را ثبت می‌کنند؛ payload خارجی و اطلاعات مهمان در لاگ نیست.

## وب‌اپ

URL جدید از `reference-city-id`، `check-in`, `check-out`, `parties` و فیلترهای query استفاده می‌کند. `parties` آرایه‌ای مانند `[{"adults":2,"childrenAges":[3]},{"adults":1,"childrenAges":[8]}]` است. sort فقط `price`, `price-desc`, `stars` است و پیش‌فرض price است. نام نمایشی مقصد از مرجع resolve می‌شود.

CityPicker داده اولیه و جستجو را از API مرجع می‌خواند؛ حداقل دو حرف، debounce ۲۵۰ میلی‌ثانیه، لغو و کنترل پاسخ دیررس دارد. خطا، تلاش مجدد، بارگذاری و فهرست خالی نمایش داده می‌شوند؛ شهر و شمارش ساختگی fallback وجود ندارد. مقاصد محبوب نیز از همان فهرست فعال شناسه می‌گیرند و لینک قدیمی تولید نمی‌کنند.

نتایج و کارت‌ها SSR، کنترل‌ها WASM island و جزئیات GUID، SSR هستند. فرم مسافر موجود WASM با prerender:false است. OfferToken، قیمت پاسخ سرور، RoomIndex و quote تازه مبنای ثبت درخواست‌اند؛ شناسه بومی یا قیمت URL معتبر نیست. draft و نتیجه ثبت با کلید حساب/پیشنهاد در sessionStorage ذخیره می‌شوند؛ شکست تبدیل Order باعث ثبت دوباره درخواست هتل نمی‌شود. مسیر HotelRequest → Orders → Checkout موجود حفظ شده است. لینک دارای city-id/city-key قدیمی پیام انتخاب مجدد مقصد می‌دهد.

## اعتبارسنجی محلی

- تست‌های Hotels شامل رفتار مرجع، مقصد خارجی/غیرفعال، نگاشت چندگانه، خطای دیتابیس، پاسخ ناقص، cancellation، قرارداد HTTP و جریان رزرو هستند.
- `HotelReferenceCityPostgresTests` فقط با متغیر صریح `REFAHI_HOTEL_TEST_DATABASE` روی دیتابیس موقت با نام `hotel_city_test*` اجرا می‌شود. از تنظیمات برنامه استفاده نمی‌کند. آزمون شامل fixture واقعی جغرافیا، اسکریپت کامل V4، توقف قبل از V4، backfill، حفظ کلیدها، نگاشت غیرفعال، خواندن موازی و تطابق مدل/migration است.
- تست‌های WebApp شامل نام/استان مرجع، اتاق‌ها، پاسخ دیررس، SSR، لینک قدیمی، جزئیات GUID، sort، CanBook، quote و retry تبدیل Order هستند.
- مرورگر با API fixture محلی: نتایج دو منبع، پیام پاسخ ناقص، جزئیات، انتخاب شهر داخلی/خارجی و فرم مسافران در اندازه موبایل بررسی شدند. اطلاعات آزمایشی استفاده شد و خرید واقعی انجام نشد.
- Service Worker موجود API را network-only و navigation را network-first نگه می‌دارد. فایل worker تغییر نکرده است.
- پروژه مستقل `tests/Refahi.Clients.Web.Modules.Checkout.Tests` در این checkout فقط bin/obj دارد و فایل csproj موجود نیست؛ مسیر تبدیل سفارش و ادامه Checkout در تست‌های Hotel پوشش داده شده است.

دیتابیس عملیاتی، staging و سرویس زنده پرووایدرها در این کار تغییر نکرده‌اند؛ نصب V4 در محیط هدف و smoke test زنده هنوز پیش‌نیاز انتشارند. استخراج سایر جدول‌های provider-owned و بازطراحی عمومی References خارج از این تغییر هستند؛ فهرستشان در provider-table-naming-audit-2026-10-19.md نگهداری می‌شود.

### نتیجه نهایی بررسی

بیلد کامل `Refahi.Backend.slnx` و `Refahi.Clients.Solution.sln` موفق بود. ۷۹ تست Hotels بک‌اند (شامل ۶ تست HTTP و آزمون PostgreSQL واقعی V4)، ۲۰ تست Hotel وب‌اپ، ۱۳ تست Orders و ۱۰ تست Wallets پاس شدند: جمعاً ۱۲۲ تست. EF تأیید کرد مدل با آخرین migration هماهنگ است. تست‌ها از snapshotهای اصلی نگاشت استفاده کردند؛ دیتابیس و سرویس‌های موقت پس از بررسی متوقف شدند. هشدارهای قبلی nullable/NuGet در بیلد باقی هستند و ارتقای وابستگی‌ها در این تغییر انجام نشده است.

### اصلاح تست دستی فاز دوم — تهران، ۲۰۲۶-۱۰-۲۰ تا ۲۰۲۶-۱۰-۲۲

در اجرای فقط لاماسو، شهر مرجع ۳۵۴ به شناسه بومی درست resolve می‌شد و Availability پاسخ HTTP 200 می‌داد؛ اما `room_rates[].price.extra_guest_price` و `extra_guest_price_to_pay` در بخش جمع قیمت null بودند. مدل مشترک قیمت روزانه/جمع، پیش از رسیدن به mapper باعث JsonException و سپس 503 عمومی می‌شد.

بخش aggregate `price` در قیمت‌گذاری استفاده نمی‌شود و از مدل نرخ حذف شد؛ منبع محاسبه همچنان `prices[]` روزانه است. nullable بودن هزینه‌های جمعی دیگر مانع خواندن پاسخ نمی‌شود، اما مبلغ null روزانه همچنان رد می‌شود و به صفر تبدیل نمی‌شود. لاگ خطای JSON اکنون فقط مسیر عملیات و JsonPath را ثبت می‌کند، بدون payload یا credential.

پنج تست بازگشت خطا اضافه شد. استعلام زنده همان مقصد/تاریخ پس از اصلاح پاسخ 200 و سه پیشنهاد معتبر داد؛ هیچ Submit، Confirm یا پرداختی انجام نشد. فعال‌سازی اصلاح در API بازشده زیر دیباگر نیازمند Rebuild/Restart است. تنظیمات فاز دوم (SnappTrip غیرفعال، Lamasoo فعال) حفظ شده‌اند.

### کنترل نسخه خروجی در تست دستی

اگر خطای اصلاح‌شده پس از Restart تکرار شد، زمان و SHA-256 فایل `Refahi.Modules.Hotels.Infrastructure.dll` در خروجی `src/Refahi.Api/bin/Debug/net10.0` با خروجی پروژه Infrastructure مقایسه شود. ساخت تست‌های ماژول به‌تنهایی خروجی Host بازشده در Visual Studio را به‌روز نمی‌کند. پیش از شروع دوباره دیباگ، خود `src/Refahi.Api/Refahi.Api.csproj` باید Build شود. اگر فایل توسط API در حال اجرا قفل است، ابتدا Stop Debugging لازم است. تکرار Restart بدون Build ممکن است همان DLL قدیمی را اجرا کند.
